# Семантическая сортировка категорий

Статус: автоопределение, поля `by`/`order` и три точки встройки (ECharts, Vega, сводная) реализованы. Порядок с API подключается провайдером. Актуальный контракт хоста — в разделе «Подключение API порядка категорий».

Задача: порядок категорий на осях, в легенде, на тепловой карте и в заголовках сводной должен быть правильным без отдельной настройки там, где порядок выводится из самих значений. Для порядков, которые из данных не выводятся (станции по маршруту, приоритет, произвольный список с API), нужен один расширяемый механизм, и он должен действовать на все типы визуализации.

Пример, из‑за которого это видно сразу: тепловая карта нагрузки. По вертикали дни недели по-русски (суббота, четверг, пятница, вторник, среда, понедельник, воскресенье), по горизонтали часы (`17, 7, 6, 18, …, 0, 3, 1, 2`). Это не календарь и не числовой порядок часов. Алфавит тоже не подходит: по-русски «воскресенье» было бы первым. Такой порядок — порядок первого появления строк в ответе запроса. Для карты нагрузки он бесполезен.

## Исходное поведение Graphic Walker (до семантической сортировки)

Отдельного типа `ISort` и ручного порядка категорий нет. Единственный пользовательский переключатель — `IViewField.sort`: `'none' | 'ascending' | 'descending'` на поле полки `encodings.rows` / `encodings.columns` (`packages/graphic-walker/src/interfaces.ts`).

Три движка читают этот флаг по-разному.

| Куда смотрит пользователь | Порядок по умолчанию (`sort: none`) | Явная сортировка asc/desc |
| --- | --- | --- |
| Vega | Домен шкалы, если его задали; иначе порядок данных | Сортировка оси по мере на другой полке (`vis/spec/encode.ts`) |
| ECharts, в том числе heatmap и pie | Порядок первого появления в `dataSource`. Для `semanticType: 'temporal'` — по времени, иначе `localeCompare` | Поле `sort` не читается. Влияет только если строки запроса уже отсортированы |
| Сводная | Всегда `localeCompare` или числовое сравнение значения измерения. Итоги в конце | Клик по заголовку. По мере сортируется только нижний уровень; родители остаются по значению измерения |

Общее для запроса:

- `getSort` (`utils/index.ts`) берёт `sort` последнего измерения на полке, где нет мер.
- Шаг `type: 'sort'` в workflow появляется только если задан `limit` (`utils/workflow.ts`). Это сортировка строк по мере, не порядок категорий.
- `IField.cmp` объявлен, но `parseCmpFunction` его игнорирует и всегда возвращает «число, иначе `localeCompare`».
- `IScale.domain: string[]` может зафиксировать порядок категорий, но только у Vega.
- `dateTimeFeature` для `month`, `quarter`, `weekday`, `week`, `hour` кладёт в данные числа (`1…12`, `0…6`, `0…23`). Если на оси остаются эти числа, числовой компаратор сводной и ECharts даёт календарный порядок. Если хост или форматтер подменяет их названиями («март», «пн»), числа теряются и порядок снова алфавитный или случайный.

Контракт встройки (`packages/graphic-walker-embed/src/contract.ts`) поля сортировки не содержит. `WalkerField` — это `fid`, `name`, `semanticType`, `analyticType`. `cube_front` не проставляет `sort` в спеках и не передаёт ни порядок станций, ни признак «это день недели». Зерно времени можно угадать только по суффиксу `fid` (`month`, `hour`, …) и по `semanticType: 'temporal'`. Cube `query.order` попадает в `provenance.query` и на порядок осей Graphic Walker не влияет.

Один и тот же `fid` в сводной и на графике делит флаг `sort` только внутри одного листа. Применяют его разные функции, поэтому заголовки сводной и ось графика для одного номинального поля сегодня не обязаны совпадать.

## Как это решено в Power BI и Tableau

Оба продукта разделяют две разные задачи. Их не стоит смешивать в одной кнопке.

**Порядок смысла поля** — свойство измерения, одно на все визуализации.

- Power BI: [Sort by column](https://learn.microsoft.com/en-us/power-bi/create-reports/desktop-sort-by-column). Колонку «Месяц» сортируют по скрытой колонке «Номер месяца». Правило жёсткое: у каждого отображаемого значения ровно одно значение ключа, и обе колонки одной гранулярности. «Январь» не сортируют по номеру дня. Порядок действует на любой визуал, где есть эта колонка. Отдельного словаря месяцев в интерфейсе нет: календарь — это обычный ключ, который модельер один раз положил рядом с названием.
- Tableau: дата несёт скрытый номер части (месяц = 1…12), подпись может быть именем. [Свойства даты](https://help.tableau.com/current/pro/desktop/en-us/date_properties.htm): дни недели сортируются по локали книги; если локаль не подходит, порядок задают вручную. [Default Properties → Sort](https://help.tableau.com/current/pro/desktop/en-us/datafields_fieldproperties.htm) задаёт порядок значений измерения по умолчанию для каждого нового представления и для списка фильтра.

**Порядок конкретного представления** — поверх порядка поля, только этот лист.

- Power BI: читатель отчёта переключает визуал на asc/desc по категории или по мере. Если дизайнер задал календарный ключ, asc/desc идёт по этому ключу, а не по алфавиту.
- Tableau, [Sort Data in a Visualization](https://help.tableau.com/current/pro/desktop/en-us/sortgroup_sorting_computed_howto.htm):
  - Data source order — порядок источника; для строк с цифрами это natural sort (`2` перед `19`, не `19` перед `2`);
  - Alphabetic — ICU, посимвольно, `19` перед `2`;
  - Field — по мере или по другому полю;
  - Manual — перетаскивание значений;
  - Nested — свой порядок внутри каждой панели, а не один порядок на весь график.

Для маршрута станций индустриальный приём один: справочник «подпись → ранг» приходит из данных или API и вешается на измерение (Power BI sort-by-column, Tableau default sort / data source order иерархии). Словарь месяцев в продукт не зашивают как единственный способ, но календарные части даты продукт узнаёт сам.

## Принцип для Graphic Walker

Пользователь карты нагрузки не должен открывать настройки, чтобы понедельник встал перед вторником, а час `0` — перед часом `10`. Настройка появляется только там, где порядок нельзя вывести: маршрут, приоритет, список с API, разовый ручной порядок одного листа.

Приоритет, сверху вниз. Сработал первый подходящий уровень — нижние не применяются.

1. **Явный порядок этого листа.** Сортировка по мере (уже есть в тулбаре и в клике по заголовку сводной) или ручной список, сохранённый на поле полки. Это сознательное действие, оно побеждает календарь.
2. **Ключ порядка поля.** Скрытое поле ранга или готовый список с хоста / API. Одно на измерение, общее для графика, тепловой карты, легенды и сводной. Аналог Power BI Sort by column и Tableau Default Properties.
3. **Автоопределение.** Срабатывает само, без флага в UI.
4. **Запасной порядок.** Natural sort: числа как числа (`0, 1, 2, 10`), прочий текст — `localeCompare` с локалью интерфейса. Порядок «как пришло из запроса» запасным не делать: на тепловой карте он и есть текущий дефект.

Уровень 1 живёт в спеке листа (`specsJson`) и уже переживает оба режима сохранения Cube Front. Уровень 2 нельзя оставлять только на `WalkerField`: при открытии поля собираются заново из Cube, и лишние свойства пропадают. Куда его писать, чтобы он доехал и в файл без строк, и в файл с данными, — в разделе «Сохранение в Cube Front». Уровень 3 в файл не пишется: он считается по строкам после открытия.

## Автоопределение

Модуль смотрит на множество значений поля, не на имя поля и не на `fid`. Имя куба и русские слова витрины в код не зашиваются.

Принять порядок, только если **все значения** узнаны одним и тем же распознавателем. Одно чужое значение — и распознаватель не применяется, проверяется следующий (иначе «Март» и «Итого» молча разъедутся). Пустые и служебные подписи (`''`, `null`, `(пусто)`, `—`, `-`) в проверке не участвуют и всегда встают в конец.

Распознаватели проверяются сверху вниз, срабатывает первый.

| # | Вид значений | Русский | Английский | Порядок |
| --- | --- | --- | --- | --- |
| 1 | Числа и числовые строки | `0`, `17`, `01`, `2.5` | то же | По числу: часы `0…23`, номера недель, день месяца |
| 2 | Даты и годы в строгом формате | `01.03.2024`, `01.03.24`, `01.03.2024 08:30`, `2024-03`, `2024-03-01`, `2024-03-01 10:00`; годы `2024 г.`, `2024 год` | ISO те же; годы `FY2024`, `FY24` | Хронология. Для формата с точками всегда «день.месяц.год», день и месяц двузначные |
| 3 | Период и год | `янв. 2024 г.`, `Январь 2024`, `март 2023`, `1 кв. 2024`, `1 полугодие 2024`, `1 пг 2024` | `Jan 2024`, `January 2024`, `2024 Jan`, `Jan-24`, `Q1 2024`, `2024 Q1`, `2024-Q1`, `H1 2024` | Год, затем номер периода. Все значения одного вида и одного языка |
| 4 | Недели | `Неделя 5`, `нед. 5`, `5 неделя`, `5 неделя 2024` | `W5`, `W05`, `Week 5`, `Wk 5`, `2024-W05`, `2024 W5`, `W5 2024` | Год, затем номер недели. Либо у всех значений есть год, либо ни у одного |
| 5 | Месяцы | `январь`…`декабрь`, родительный `января`…`декабря`, краткие `янв`, `фев`/`февр`, `мар`, `апр`, `май`, `июн`, `июл`, `авг`, `сен`/`сент`, `окт`, `ноя`/`нояб`, `дек` | `January`…`December`, `Jan`…`Dec`, `Sept` | Январь…декабрь |
| 5 | Дни недели | `понедельник`…`воскресенье`, `пн`…`вс`, `пнд`…`вск` | `Monday`…`Sunday`, `Mon`…`Sun`, `Tue`/`Tues`, `Thu`/`Thur`/`Thurs` | Для ru с понедельника, для en с воскресенья |
| 5 | Кварталы | `1 кв`, `кв 1`, `кв. 1`, `кв.1`, `1 квартал`, `1-й квартал`, `I кв`, `I квартал` (до `IV`) | `Q1`, `Qtr 1`, `Quarter 1`, `1st quarter`, `1Q` | По номеру |
| 5 | Полугодия | `1 полугодие`, `I полугодие`, `1-е полугодие`, `1 пг` | `H1`, `1st half`, `first half` | Первое, затем второе |
| 6 | `semanticType: 'temporal'`, значение разбирает `new Date` | — | — | Хронология |
| 7 | Всё остальное | | | Natural sort с локалью интерфейса |

Регистр, лишние пробелы и точка в конце не мешают узнаванию («Пн.», «ЯНВ», « март »). На оси остаётся исходная подпись.

Если русские названия пришли при английском интерфейсе, порядок всё равно русский: язык определяется по самим значениям. Локаль интерфейса нужна только для разрешения неоднозначности.

Новый язык подключается через `registerCategoryCalendar` (`sort/calendars.ts`): его месяцы, дни, кварталы и полугодия автоматически работают и в одиночку, и в сочетании с годом.

Намеренно не распознаётся:

- `дд/мм/гггг` — неотличимо от американского `мм/дд/гггг`. Такие строки идут через шаг 6, если поле временное, иначе natural sort.
- Русские и английские подписи в одном поле («март» и «March», «1 кв» и «Q1»).
- Недели с годом и без года в одном поле.
- Номера версий вида `1.2.10`: формат с точками требует двузначных дня и месяца.

Часы на карте нагрузки закрывает первый распознаватель, даже если Cube отдал их строками. Дни недели на той же карте закрывает словарь дней. Отдельной настройки «это тепловая карта станций» не нужно.

Не угадывать маршрут, алфавит линий, приоритет «высокий / средний / низкий» на нескольких языках. Ложных автоматических порядков хуже, чем честный алфавит.

## Расширение для API и ручных случаев

Два необязательных поля на измерении. Оба аддитивные: старые спеки и `WalkerField` без них работают как сейчас.

```ts
/** Порядок категорий измерения. Общий для всех визуализаций датасета. */
interface CategoryOrder {
  /** fid скрытого поля ранга в той же строке. Меньше — раньше. */
  by?: string;
  /** Готовый список подписей, например станции по ходу маршрута. */
  order?: string[];
}
```

`by` — путь Power BI. Хост кладёт в строки ранг и не выводит его на полку. Каждой подписи соответствует один ранг; если в данных у одной станции два ранга, ключ считается сломанным, порядок не применяется, значения остаются на запасном natural sort. Ранг в запрос сводной и графика добавляется как скрытое измерение: при отношении 1:1 зерно не меняется.

`order` — путь Tableau Manual и ответ API «последовательность станций». Значения из списка идут в заданном порядке. Значения, которых в списке нет, встают в конец и между собой сортируются natural sort, а не пропадают. Общий список для всех листов хост кладёт на поле датасета и при открытии переносит по `fid` (см. «Сохранение в Cube Front»). Копия в спеке одного листа — только переопределение этого листа.

Ручной порядок одного листа — тот же `order`, но на `IViewField` внутри спеки. Он не переписывает порядок измерения для других графиков.

`cmp?: string` для этого не использовать. Это мёртвая строка, её никто не читает, и компаратор строкой плохо сериализуется в `specsJson`.

В контракт embed те же поля добавляются опционально. Обязательные `fid`, `semanticType`, `analyticType`, `specsJson` и ключи `provenance` не меняются. Пока хост ничего не прислал, библиотека живёт на автоопределении. Сама запись поля в `WalkerField` сохранение не гарантирует: открытие файла это поле выбрасывает. Ниже — что именно доезжает до диска.

## Сохранение в Cube Front

Диалог сохранения визуализации пишет один JSON двумя вариантами (`useSaveDialog`, `visualizationCodec.serialize`). Слоты в обоих файлах без строк. Строки есть только у Walker и только во втором варианте.

| | Только конфигурация | С данными |
| --- | --- | --- |
| Режим диалога | `config` | `report` |
| `variant` файла | `config` | `snapshot` |
| Артефакт | `cube-gw-config` | `cube-gw-report` |
| Расширение | `.cube-config.json` | `.cube-report.json` |
| Что внутри Walker | `id`, `name`, `fields`, `specsJson`, `provenance` | то же плюс `datasets[].rows` |
| Каталог | этот вариант туда кладётся (`isVisualizationConfigStorable`) | нет |
| Открытие | запрос в Cube заново (`hydrateOpenedSlots`, режим `refresh`) | строки из файла, Cube не вызывается |

Перед сохранением отчёта с данными снимок снимается с движка (`refreshSnapshots` → `exportReport`). Конфигурация без данных обновляет снимок при открытии диалога (`refreshConfigSnapshot` → `exportConfig`). Оба экспорта сначала забирают спеки из движка (`syncSpecsFromProvider`) и кладут их в `specsJson` как есть. Сортировка попадёт в файл, только если она уже записана в спеку листа.

Спека листа — это `exportAllCharts`: массив истории `{ base, timeline }`, внутри `base.encodings`. Туда входит и нынешний `IViewField.sort`. Хост эту строку не разбирает.

При открытии обоих вариантов поля не читаются из файла. `reconcileWalkerConfigWithSlots` подставляет набор из `buildSlotWalkerFieldsForOpen` → `mapCubeResultToWalker`. У нового поля только `fid`, `name`, `basename`, `semanticType`, `analyticType`. `specsJson` остаётся целиком, если каждый `fid` внутри `encodings` всё ещё есть среди новых полей (`resolveReplaceSpecs`). Пропал один `fid` — графики датасета сбрасываются в `[]`, вместе с ними и порядок на полках.

Слоты режут ещё сильнее. `snapshotToQuerySlotDefinition` оставляет от поля `key`, `label`, `role`, `dataType`. `basename` и любое будущее свойство порядка там не живут.

`provenance` при согласовании не трогается, но это не место для порядка. Следующая подмена датасета (`buildWalkerInput`) пишет его заново: `cubeName`, `cubeTitle`, `groups`, `queryFingerprint`, `query`. Чужой ключ в этот объект не переносится.

Отсюда три правила, иначе сортировка есть в сессии и пропадает после сохранения.

1. **Порядок этого листа** (сортировка по мере и ручной список одной полки) писать в `encodings` спеки. Он уже едет в оба файла и возвращается при открытии. Нельзя добавлять в кодировки `fid` ранга, которого нет в результате Cube: проверка спеки сотрёт все графики датасета, не только одну ось.
2. **Порядок измерения** (`order: string[]`, маршрут станций) — список подписей, не колонка в строках. В конфигурации без данных строк нет, после открытия придут новые. Список от строк не зависит, поэтому переживает оба режима. Хранить его в спеке (свойство поля полки, не новый `fid`) либо на поле датасета, но тогда `reconcileWalkerConfigWithSlots` обязан перенести его со старого поля на новое по `fid`. Без этого переноса поле в файл запишется и при открытии исчезнет. Пока `walkerFieldToDatasetField` его не копирует, слот этот список не сохранит.
3. **Ключ `by`** (скрытая колонка ранга) работает в режиме конфигурации только если колонка входит в запрос Cube: открытие выполняет запрос заново, лишних колонок в ответе не будет. В снимке с данными колонка останется в `rows`, только если она там была на момент сохранения. Схема полей всё равно строится из запроса, не из лишних ключей строк.

Автоопределение календаря и чисел в файл не пишется. После конфигурации оно считается по свежим строкам, после снимка — по сохранённым. Отдельной настройки в JSON для «март перед январём» не нужно.

## Куда встраивать

Одной существующей функции недостаточно. Запрос, Vega, ECharts и сводная расходятся после агрегации, а сводная ещё раз сортирует дерево сама.

Новый чистый модуль, без React:

`packages/graphic-walker/src/sort/categoryOrder.ts`

Вход: поле, список значений, строки (чтобы прочитать ранг `by`), локаль, явный override листа.
Выход: упорядоченный домен `string[]` и компаратор «индекс в домене».

Его вызывают три места. Это и есть вся встройка; четвёртый движок не заводится.

| Место | Зачем |
| --- | --- |
| `orderedAxisValues` / `uniqueValues` в `vis/echarts/toEchartsOption.ts` | Тепловая карта, pie, легенда, категории ECharts. Сейчас здесь порядок первого появления |
| `channelEncode` в `vis/spec/encode.ts` и домен в `resolveScales` | Vega. Если пользователь выбрал сортировку по мере — оставить нынешний `{ encoding, order }`. Иначе `sort` = домен из модуля |
| `comparePivotSortValues` в `components/pivotTable/utils.ts` | Заголовки сводной. Сравнение по индексу домена вместо голого `localeCompare`. Сортировка по мере на листе по-прежнему подменяет ключ нижнего уровня |

`toWorkflow` для этой задачи не подходит как единственная точка. Шаг сортировки включается только вместе с `limit` и сортирует строки по мере. Сводная после этого всё равно пересобирает дерево. Календарный порядок — это порядок домена после агрегации, его не нужно тащить в SQL.

`parseCmpFunction` тоже не точка расширения. Туда можно отдать уже готовый компаратор модуля для клиентского `sortBy`, но решение о порядке принимается в `categoryOrder.ts`.

Фильтр distinct-значений (`computation/index.ts`) стоит подключить тем же компаратором вторым шагом: список фильтра с днями недели в алфавитном порядке снова ломает ожидание. На первую версию осей и сводной это не блокирует.

## Поведение по кейсам

**Часы, номера недель, кварталы числом.** Автоопределение, уровень 3. Ось `0…23`, недели по номеру. В сводной то же сравнение.

**Названия месяцев и дней, ru и en.** Автоопределение по словарю, включая краткие формы `Intl` («февр.», «нояб.») и родительный падеж. Смешанный язык в одном поле (часть «March», часть «март») словарём не считается.

**Месяц, квартал или полугодие с годом.** «янв. 2024 г.», «1 кв. 2024», «Q1 2024», «H1 2024» сортируются по году, затем по периоду. Это типичная подпись оси, когда хост форматирует зерно `month` или `quarter`.

**Даты строкой.** `дд.мм.гггг` и ISO сортируются по хронологии при любом `semanticType`: Cube Front может отдать уже отформатированную дату как номинальное поле.

**Зерно `dateTimeFeature`, значение ещё число.** Ничего настраивать не надо: числовой порядок уже правильный, модуль его сохраняет и распространяет на сводную.

**Станции по маршруту.** Хост получает последовательность с API и пишет `order` на поле датасета. Список подписей не зависит от строк, поэтому он есть и в файле без данных, и в файле со строками — если при открытии его перенесли по `fid`. Колонка ранга `by` годится только если она входит в запрос Cube: иначе режим «только конфигурация» после повторного запроса её потеряет. Новая станция, которой нет в списке, видна в конце, а не теряется.

**Сортировка по нагрузке.** Остаётся действием пользователя: тулбар asc/desc или клик по заголовку сводной. Для карты нагрузки это не значение по умолчанию. По умолчанию у карты календарные оси, даже если суббота темнее понедельника.

**Вложенная сортировка Tableau Nested** (внутри каждой панели свой порядок по мере) в первую версию не входит. Сейчас сводная и так сортирует по мере только лист. Это отдельное решение, его не смешивать с порядком смысла поля.

## Что увидит пользователь

Пока поле узнаётся или у него есть ключ с хоста, новых контролов нет. Пилюля измерения не обрастает мастером «тип сортировки».

Когда автоопределения нет и хост не прислал ключ, порядок natural sort. Для короткого домена (ориентир — до 30 значений) на поле полки достаточно одного действия «задать порядок»: список с перетаскиванием, запись в спеку листа. Это эквивалент Tableau Manual и нужно для разового отчёта, не для календаря.

Сортировка по мере остаётся там, где она уже есть: тулбар графика и цикл по заголовку сводной. Подпись режима должна говорить, что сортируется (мера или категория), чтобы календарный порядок нельзя было случайно принять за «сломанную» сортировку по цвету.

## Срезы реализации

1. Модуль домена и тесты Jest: числа, месяцы ru/en, дни с понедельника и с воскресенья, кварталы, неизвестное значение отменяет словарь, хвост неизвестных станций, конфликт двух рангов у одной подписи.
2. Три вызова: ECharts, Vega, сводная. Одна фикстура «дни × часы» даёт один и тот же порядок на heatmap и в сводной.
3. Опциональный `CategoryOrder`. Список `order` — в спеке листа, чтобы его не стёрло открытие. Ключ `by` — только для колонки, которая есть в запросе Cube. Если порядок вешают на поле датасета, `reconcileWalkerConfigWithSlots` переносит его по `fid` и в конфигурации, и в снимке. Старые спеки не мигрируют.
4. Ручной список на поле полки и общий порядок в фильтре — после того, как оси и сводная совпадают.

Публичный `index.tsx` и обязательные поля контракта на срезах 1–2 не меняются. Срез 3 — добавление необязательного поля, его делает задача на контракт, не попутная правка heatmap.

## Подключение API порядка категорий

Без провайдера кнопки на пилюле нет, автоопределение работает как раньше. Если провайдер передан, на пилюле измерения есть действия «Порядок из API» и «Сбросить порядок».

Провайдер Graphic Walker (прямое использование редактора):

```ts
categoryOrderProvider?: (request: ICategoryOrderRequest) => Promise<CategoryOrder | null>

interface ICategoryOrderRequest {
  field: { fid: string; name: string; semanticType: ISemanticType }
  datasetId?: string
}

interface CategoryOrder {
  by?: string
  order?: string[]
}
```

У `GraphicWalker` нет id датасета хоста. В контекст кладётся уже готовая функция; `datasetId` подставляет embed.

Контракт embed, чтобы `cube_front` не импортировал типы Graphic Walker:

```ts
categoryOrderProvider?: (request: WalkerCategoryOrderRequest) => Promise<WalkerCategoryOrder | null>

interface WalkerCategoryOrderRequest {
  datasetId: string
  fid: string
  name: string
  semanticType: string
}

interface WalkerCategoryOrder {
  by?: string
  order?: string[]
}
```

Куда передать: `createGraphicWalkerHost(el, { maxDatasets, categoryOrderProvider })`. `maxDatasets` обязателен, провайдер — нет.

Что вернуть:

- `order` — список подписей в нужном порядке. Значений вне списка рендер не выкидывает.
- `by` — `fid` скрытой колонки ранга в той же строке. Имеет смысл только если эта колонка есть в запросе Cube: открытие конфигурации запрашивает Cube заново.
- `null` — у API нет порядка для поля. Остаётся автоопределение.

Куда пишется: выбранный порядок становится полем полки в спеке листа (`IViewField.categoryOrder`) и уходит в `specsJson`. Открытие файла спеку сохраняет. Автоопределение в файл не пишется.

Заготовка для `cube_front`. Путь запроса здесь не настоящий эндпоинт:

```ts
import { createAuthenticatedClient } from '@/services/http'
import { createGraphicWalkerHost } from '@cube/graphic-walker-embed'
import type { WalkerCategoryOrder, WalkerCategoryOrderRequest } from '@cube/graphic-walker-embed/contract'

const http = createAuthenticatedClient({ baseURL: '' })

await createGraphicWalkerHost(el, {
  maxDatasets: 8,
  async categoryOrderProvider(request: WalkerCategoryOrderRequest): Promise<WalkerCategoryOrder | null> {
    const { data } = await http.post<WalkerCategoryOrder | null>('/category-order', {
      datasetId: request.datasetId,
      fid: request.fid,
    })
    if (!data) return null
    if (data.by) return { by: data.by }
    if (data.order?.length) return { order: data.order }
    return null
  },
})
```
